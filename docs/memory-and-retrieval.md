# 三层记忆与检索注入

长篇（数百章）创作的核心矛盾：**上下文装不下全书，而模型必须"记得"前面写过什么。**

天真的做法是把前面所有章节塞进提示词——几百章就是几十万 token，既超窗口又贵得离谱，
而且模型对长上下文中部的信息利用率会显著下降。所以"记住什么"必须变成一个**检索问题**。

## 三层记忆

记忆不是一个大池子，而是按**视角**分成三层——因为不同信息应该在什么时机、以什么身份出现，
是不一样的：

| 层 | 内容 | 用途 |
|---|---|---|
| **全知事件** | 客观发生了什么（谁在哪一章做了什么） | 情节连续性、伏笔回收 |
| **限知角色经历** | 某个角色**亲身经历/亲眼看到**的事 | 角色视角写作，避免"上帝视角"穿帮 |
| **信息 · 知晓 · 伏笔** | 谁知道什么、什么还没回收 | 防信息泄露、伏笔闭环 |

第二层是全知第一层的**投影**，但它们必须分开存——因为写作时要保证：
**角色只能基于"他知道的事"行动**。

这就是长篇里最容易崩的一类 bug：第 30 章角色 A 说出了一件只有角色 B 知道的事。
如果只有"全知事件"一层，模型看不到"谁知道什么"，这个错误**无法被检测**。

## 事件日志 ≠ 现状

三层记忆是**事件日志**（发生了什么）。但写作还需要**现状**——"现在"是什么状态：

- 角色现在什么修为/等级/职务，谁已经死了或退场了
- 领地等级、兵力、势力范围的当前值

现状不能靠"把事件日志从头折叠一遍"得到——成本高、且模型会算错。所以现状是**独立维护的快照**，
每章定稿后随记忆提取一起更新，并带两个守卫：

- **单调守卫**：已推进到第 15 章的状态，不能被第 12 章的信息回退覆盖
- **只写模型明确给出的字段**：模型没提的字段保持原值，而不是猜一个
- **锁定字段**：用户可以标记某字段"不自动改"（比如他心里的设定与模型推断不一致时）

现状会被拼接成一行【当前状态（实际，以此为准）】注入上下文——
**当事件日志与现状冲突时，以现状为准**，因为这正是"折叠"后的权威结果。

## 注入：检索决定用什么，预算决定用多少

```
章节细纲 + 角色名单
        │
        ▼
   构造查询词（完整短语 + 3 字 n-gram）
        │
        ▼
  按作用域取候选 ──► BM25 召回 ──► 语义重排 ──► RRF 融合 ──► 相关性门槛
        │                                              │
        │                                      （词面为空时走语义兜底）
        ▼
   预算裁剪（各类别各有上限，超出按重要度+新鲜度截断）
        │
        ▼
   三段式注入：铁律设定 / 相关记忆 / 当前状态
```

检索模块的实现与设计说明见 [`../examples/retrieval/`](../examples/retrieval/)。
这里只强调三个原则：

**① 召回池决定上限。** 精排只能重排池子里的东西。召回不到，后面再精细也没用。

**② 门槛比召回率重要。** 无关记忆注入不是"无用的噪声"，而是**主动的错误来源**——
模型会把不相关的旧设定当成前提，编造出关联。所以 `fallback_top_n` 默认 0：
没有可靠的检索结果时，宁可不注入。

**③ 预算裁剪要按类别分配**，不能全局 top-k。世界观铁律、角色经历、未回收伏笔各有配额——
否则角色经历多的小说会把伏笔挤出去，而伏笔恰恰是最不能忘的那一类。

## 一致性审校

生成之后还有一道独立检查，扫描七类问题：

```
timeline         时间线矛盾（同时出现在两地、时序错乱）
setting          世界观设定冲突
character        角色设定/腔调不符
memory_conflict  与既有记忆矛盾
knowledge_leak   角色使用了不该知道的信息
promise_break    承诺/伏笔被无解释地打破
ai_flavor        语言同质化、套话堆砌
```

这道检查的**准确率是可量化的**——见 [`../evals/`](../evals/)：
20 条人工标注评测集、两级匹配指标、可复现的自检链路。

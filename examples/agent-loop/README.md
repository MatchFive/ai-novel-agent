# Agent 循环示例：审批闸门与工具门禁

```bash
python demo.py
```

```
demo.py           演示：门禁派生对比 + 审批裁决 + 超时恢复
approval_gate.py  实现：RunState / 交付物闭包 / ApprovalGate
```

从生产代码简化而来（去掉数据库持久化与 Web 层），保留三样真正重要的东西：
**并发控制、门禁判定、状态机**。

---

## 一、门禁：为什么是白名单 + 依赖闭包

Agent 自主创作最大的风险不是"做不出来"，而是**做多了**。

用户说「只写第 3~5 章」，Agent 手里却有重建世界观的权限——它迟早会顺手把世界观改掉，
而且是在你没看的时候。旧版用「四档枚举」（讨论/编辑/规划/全流程）来限定范围，
结果是**组合需求被逼进错误的桶**：「改主角卡 + 出大纲」卡在规划档靠模型自觉；
「只写第 3~5 章」只能选"全流程"，等于默许动所有东西。

现在的做法是三层：

```
封闭词表多选          →  依赖闭包            →  fail-closed 白名单
world / characters /       chapters 带 outline     未列出 = 不可用
outline / chapters /       draft 带 chapters       新工具默认拒绝
draft / edit
```

关键在 **draft 只带 chapters、不带 world/characters**：
正文依赖细纲（没细纲写不了正文），但**不依赖世界观重建**。
所以「只写正文」不会顺势扩建成"重建世界观 + 重写角色 + 重排大纲"。

`resolve_deliverables()` 是纯函数，同样输入永远同样输出——
授权范围可以**推导**、可以**测试**，不依赖模型是否"听话"。

## 二、闸门：Agent 停下等人

自主 Agent 一口气把整本书规划完再交付是不行的，中途需要人审。
但人可能半小时后才回来，所以等待机制要满足四个条件：

| 要求 | 实现 |
|---|---|
| 能挂起 | `asyncio.Event` + `wait_for`，不阻塞事件循环 |
| 超时不失败 | 超时转 `paused`（**不是** `failed`），现场保留 |
| 能恢复 | 用户回来接着推进，不用重跑前面几十步 |
| 裁决幂等 | 只有仍在等待的请求会被唤醒；重复提交返回 `False` 而非报错 |

最后一条容易忽略但很重要：**接口重试是常态**（前端超时重发、用户手抖点两次），
如果重复提交会抛异常或重复唤醒，任务状态就乱了。

### 为什么要两道门，而不是一道

线上有**规划确认**和**选项确认**两道门，复用同一套机制但问的东西不同：

- **规划确认** —— 审核结构化的卷 / 情节 / 章节。没有结构化规划时会**拒绝**（它只认结构）。
- **选项确认** —— 把「在多个方案里挑一个」交给人（金手指、书名、剧情走向）。

第二道门是踩坑后加的：此前 Agent 只能把候选方案写进自由文本里干等——
**前端没有可点的东西，用户只能自己打字**，而任务已经被标记完成
（真实事故：Agent 抛出 5 套候选金手指，用户无处可选）。

教训是：**让人做选择，就要给出可选择的界面**，光有文本通道不算人工介入。

## 三、关于状态机的一段弯路

早期版本用过 7 阶段状态机（立项 → 世界观 → 人物 → 大纲 → 正文 → 验收 → 收束），
后来**整体移除**了，改成目标驱动的纯 ReAct：由代码算出【进度摘要】，
模型据此自主决定推进顺序，"能做什么"仍由白名单裁定。

移除的原因是：固定阶段推进靠模型自觉、阶段验收靠自由裁量，反而更脆弱——
模型明明可以把世界观和角色一起补完，却被阶段门卡住，或者为了通过阶段门而空转。
**该强约束的地方是权限（白名单），不是流程顺序。**

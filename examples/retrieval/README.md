# 混合检索示例

从生产代码抽出的检索模块，去掉配置依赖后可直接运行：

```bash
python demo.py
```

```
demo.py              演示：15 条记忆库 + 5 个真实查询
hybrid_retrieval.py  实现：BM25 召回 → 语义重排 → RRF 融合 → 相关性门槛
```

## 为什么是「词面 + 语义」两级，而不是只用一个

| 方案 | 问题 |
|---|---|
| 只用向量检索 | 中文专有名词（人名、地名、自造词）向量区分度差；且要额外维护向量库 |
| 只用 BM25 | 同义改写、语义相关但字面不同就召回不到 |
| **两级 + RRF 融合** | 词面保证精确命中，语义补足同义；**RRF 只用名次**，规避两套分数不可比的问题 |

## 三个值得注意的实现决策

**① 召回层用 Python 侧 BM25，不是数据库全文索引。**
线上早期用 SQLite FTS5 + `bm25()`，迁到 PostgreSQL 后自带全文检索对中文分词不友好。
而单项目语料规模小（通常 < 数千条），DB 只负责按作用域取候选、打分在进程内完成，
反而更好控制——这也是「查询词用字符 trigram」这个设计的由来：不需要分词器。

**② 相关性门槛比召回率更重要。**
BM25 分数在小语料下会趋近 0 而失去区分度，这时自动退化为「查询词覆盖率」判据
（`rank_candidates` 里的 `discriminative` 分支）。
更关键的是 `rank_fallback` 的默认行为：**无语义可用时 `fallback_top_n = 0`，即宁可不注入**。
把无关记忆塞进上下文，模型会凭空编造出关联——这比少注入几条危害大得多。

**③ 同步 CPU 必须挪出事件循环。**
分词 + 打分是纯 CPU 循环。asyncio 单线程下直接在协程里跑会冻住整个服务
（线上真实事故：一次手册检索触发同步嵌入，`/api/health` 都超时、页面全白，
而机器其它核还闲着）。所以有 `bm25_rank_async` / `rank_candidates_async` 这层包装。

## 关于召回池的一点提醒

`rank_candidates` 只能**重排**传给它的候选池，**不能捞出池子外的东西**——
召回池决定上限。所以要提升召回，应该先改召回层（查询词构造、`recall_k`），
而不是调精排参数。

`demo.py` 末尾的对照实验展示了这一点：短关键词「沈昭玉佩」召回 0 条，
而自然句子「沈昭带着那枚断裂的玉佩，想起老者当年的叮嘱」召回 1 条。
原因是 2 字人名在 3 字 trigram 语料里没有对应 token——
线上把「章节大纲 / 情节描述」作为查询文本，天然规避了这个问题。
